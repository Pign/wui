# CLI Reference

The `wui` CLI tool scaffolds, builds, runs, and cleans wui projects. Install it via haxelib:

```bash
haxelib install wui
```

Then invoke as:

```bash
haxelib run wui <command> [options]
```

Or, if you add haxelib's bin to your PATH:

```bash
wui <command> [options]
```

---

## Commands

### init

```bash
wui init [name]
```

Scaffold a new wui project. Defaults to `MyApp` if no name is given.

The project directory keeps the user-provided name (so `wui init my-app` creates `my-app/`), while the Haxe class and source file use a PascalCase form (`MyApp.hx`, `class MyApp`) so the result compiles even when the input has dashes, underscores, dots, or mixed case.

Creates:

```
<name>/
  src/
    <ClassName>.hx   # main App class (PascalCase form of <name>)
  build.hxml          # Haxe build configuration
  wui.json            # project metadata
```

The generated `build.hxml` includes `-lib wui`, registers the `WinUIGenerator` macro, and sets the hxcpp flags wui's pipeline needs (`-D static_link -D HXCPP_M64`). The generated source extends `wui.App` with a minimal `body()`.

**Example:**

```bash
wui init TodoApp
cd TodoApp
wui run
```

---

### build

```bash
wui build [options]
```

Compile the project through the full pipeline:

| Step | What happens |
|------|--------------|
| **1/3** Haxe compilation | Runs `haxe build.hxml`. Haxe drives hxcpp to compile the Haxe sources into a static C++ library (`build/cpp/lib<AppName>.lib`). The WinUIGenerator macro emits C++/WinRT source into `build/winui/`. |
| **2/3** NuGet restore | Restores Windows App SDK, CppWinRT, ImplementationLibrary, and SDK Build Tools packages into `build/packages/`. |
| **3/3** MSBuild | Builds the `.vcxproj` against the hxcpp lib + NuGet packages to produce a self-contained native `.exe`. |

Output: `build/winui/<arch>/<Config>/<AppName>.exe`

Requires `wui.json` and `build.hxml` in the current directory.

---

### run

```bash
wui run [options]
```

Build (if needed) then launch the `.exe`. Accepts the same options as `build`.

---

### clean

```bash
wui clean
```

Delete the entire `build/` directory (hxcpp output, generated C++/WinRT, NuGet packages, and compiled binaries).

---

### help

```bash
wui help
```

Print usage information and list all commands.

---

### version

```bash
wui version
```

Print the wui version.

## Options

Options can be passed to `build` and `run`:

| Option | Description | Default |
|--------|-------------|---------|
| `--release` | Build with the Release configuration (optimized, no debug symbols). | Debug |
| `--arch=ARCH` | Target architecture. Values: `x64`, `arm64`. | `x64` |
| `--verbose`, `-v` | Show full MSBuild output instead of minimal. | off |

**Examples:**

```bash
wui build --release
wui build --arch=arm64
wui run --release --verbose
wui build --release --arch=arm64 -v
```

## wui.json

Every wui project has a `wui.json` in its root. This file configures the build.

```json
{
    "appName": "MyApp",
    "packageName": "com.haxe.myapp",
    "displayName": "My App",
    "windowsAppSdkVersion": "1.5.240627000",
    "targetFramework": "net8.0-windows10.0.22621.0",
    "architecture": "x64",
    "debugConsole": false
}
```

### Fields

| Field | Type | Description |
|-------|------|-------------|
| `appName` | string | Internal name. Used for the `.vcxproj`, `.exe`, the App C++ class, and the C++ namespaces. |
| `packageName` | string | Reverse-domain package identifier. |
| `displayName` | string | Human-readable name. *Not currently used for the window title* — the title comes from the `appName():String` override on your App subclass, falling back to the Haxe class name. |
| `windowsAppSdkVersion` | string | **Concrete** Windows App SDK NuGet version. The `.vcxproj` imports props/targets from `..\packages\Microsoft.WindowsAppSDK.<version>\...` literally, so wildcards like `1.8.*` would break the imports and are rejected with a warning (fallback to the built-in default). Pick a specific build of the SDK that's available on your NuGet feed. |
| `targetFramework` | string | Target framework moniker. |
| `architecture` | string | Default build architecture (`x64` or `arm64`). Overridden by `--arch`. |
| `debugConsole` | bool | If `true`, the generated `wWinMain` allocates a Win32 console at boot and redirects `stdout`/`stderr`/`stdin` to it. `Sys.println`, `printf` and `std::cout` then become visible alongside the GUI window. Useful for development; ship with `false`. |

## build.hxml

The Haxe build file. Generated by `wui init`, but you can edit it freely.

```hxml
-cp src
-lib wui
--macro wui.macros.WinUIGenerator.register()
-main MyApp
-cpp build/cpp
-D static_link
-D HXCPP_M64
```

Key entries:

- `-lib wui` — pulls in the wui library from haxelib.
- `--macro wui.macros.WinUIGenerator.register()` — registers the code generation macros that run during and after typing.
- `-cpp build/cpp` — hxcpp output directory.
- `-D static_link` — tells hxcpp to produce a static `.lib` (consumed by the MSBuild `.vcxproj`) instead of a standalone `.exe`. **Required** — without it, MSBuild has nothing to link the Haxe runtime into the WinUI 3 binary.
- `-D HXCPP_M64` — forces hxcpp to compile for x64. Without it, hxcpp defaults to x86 on Windows and the resulting `.lib` symbol-mangles differently than the x64 MSBuild side, leading to `LNK2001 unresolved __hxcpp_lib_main`.

You can add additional `-cp`, `-lib`, or `-D` flags as needed. A common addition for client code is `--macro nullSafety("<your.package>", Strict)`.
